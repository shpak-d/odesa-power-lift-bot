# Світло й ліфт: вебмоніторинг ДТЕК в Одесі

Python 3.11+, aiogram 3, asyncio, httpx, SQLite, Docker Compose. Стежить за чергою
квартири **2.1** і другою лінією **4.1** одного оператора — **ДТЕК Одеські електромережі**.
Потенційний простій ліфта — перетин відключень обох ліній. Це прогноз за планом,
а не показання датчика чи фактичний статус ліфта.

**Типовий режим — вебсторінка без Telegram.** Графіки перевіряються кожні 10 хвилин,
навіть якщо Telegram недоступний або токен не заповнений. На сторінці є сьогодні/завтра,
шкала двох ліній, перетини відключень для ліфта, давність даних і стан джерела.

## Швидке оновлення вже встановленого проєкту

У наявному каталозі на Linux Mint:

```bash
git pull --ff-only
docker compose up -d --build
docker compose logs --tail=50 bot
```

Якщо ви вже додавали `APP_MODE` у `.env`, установіть `APP_MODE=web`.
Якщо змінної немає, буде обрано вебрежим. Наявний SQLite volume з графіками зберігається.
Відкрийте **http://127.0.0.1:8080/** у браузері на цьому ж комп'ютері Linux Mint.
Telegram-запити та сповіщення у вебрежимі не виконуються.

Сторінка читає останній стан SQLite кожні 30 секунд; це не додаткове опитування ДТЕК.
При збої джерела графіки залишаються видимими з попередженням. Коли на дату ще немає
опублікованого плану, сторінка прямо повідомляє про відсутність даних.

Для доступу з телефона або іншого комп'ютера у вашій домашній мережі додайте у `.env`
`WEB_BIND=0.0.0.0`, виконайте `docker compose up -d` та відкрийте `http://IP_СЕРВЕРА:8080/`.
Адресу сервера можна подивитися командою `hostname -I`. Сторінка не має авторизації;
типове прив'язування порту до `127.0.0.1` залишає її доступною лише локально.

Доступні read-only маршрути: `/`, `/api/dashboard`, `/healthz`.
`/healthz` перевіряє життя вебрежиму та циклу моніторингу, а не доступність ДТЕК.

## Запуск на Linux Mint через Docker Compose

Потрібні Git, Docker Engine і Compose v2. Для Mint використовуйте інструкцію
[Docker для похідних Ubuntu](https://docs.docker.com/engine/install/ubuntu/), обравши
відповідну базову версію Ubuntu. Команди нижче виконуються в терміналі Linux.

1. Клонуйте репозиторій і перейдіть у каталог проєкту:

   ```bash
   git clone https://github.com/shpak-d/odesa-power-lift-bot.git
   cd odesa-power-lift-bot
   ```
2. Створіть `.env`:

   ```bash
   cp .env.example .env
   chmod 600 .env
   nano .env
   ```

3. Залиште `APP_MODE=web`. Для вебсторінки `BOT_TOKEN` і `ALLOWED_CHAT_IDS` не потрібні.
   Черги й оператор уже налаштовані: ДТЕК, 2.1 та 4.1.
4. Зберіть образ та перевірте джерело **без запуску Telegram polling**:

   ```bash
   docker compose build
   docker compose run --rm --no-deps bot python -m schedule_provider --check
   ```

   Команда повертає нормалізовані реальні дані для двох дат і черг у JSON.
   Час інтервалів у JSON — UTC з `+00:00`; вебсторінка та Telegram показують київський час.
   `status: missing` означає відсутність опублікованого графіка.
   При помилці джерела код завершення — 1. Демонстраційних даних як запасного
   джерела немає. Перевірка не змінює SQLite і не надсилає повідомлень.
5. Запустіть **один** екземпляр:

   ```bash
   docker compose up -d
   docker compose ps
   docker compose logs --tail=100 -f bot
   ```

6. Відкрийте http://127.0.0.1:8080/ у браузері на Linux Mint.

Docker має запускатися при завантаженні системи:

```bash
sudo systemctl enable --now docker
```

Контейнер має `restart: unless-stopped`, обмежені логи, непривілейованого користувача,
read-only кореневу файлову систему й постійний volume `bot_data` для SQLite.
Вимкніть автоматичний сон Linux Mint, якщо машина має працювати цілодобово.

підміні походження або оператора графіка.

## Telegram поруч із вебсторінкою

Залиште `APP_MODE=web` і поточні `WEB_PORT` / `WEB_BIND` у `.env`.
Заповніть `BOT_TOKEN` та `ALLOWED_CHAT_IDS` числами через кому. Для груп потрібен
ID групи (зазвичай від'ємний); у приватному чаті — User ID.
Якщо ручний Telegram-тест ще працює, зупиніть його через `Ctrl+C` перед запуском сервісу.

```bash
git pull --ff-only
docker compose up -d --build --no-deps telegram
docker compose ps
docker compose logs --tail=100 -f telegram
```

З'явиться постійний контейнер `odesa-power-lift-telegram` із `restart: unless-stopped`.
Явне зазначення сервісу активує його профіль `telegram`; звичайний вебзапуск не потребує
Telegram-токена. Чинний сервіс `bot` та його порт не змінюються й не перезапускаються
цією командою. `Ctrl+C` у `logs -f` завершує лише перегляд логів; сервіс працює далі.

Кожен контейнер має власну постійну SQLite: веб — `bot_data`, Telegram — `telegram_data`.
Це зберігає ідентифікатор допису, історію доставки та backoff після перезапуску Telegram.
Кожен режим самостійно отримує графіки ДТЕК раз на `CHECK_INTERVAL_MINUTES`.
Для оновлення чи перезапуску лише Telegram використовуйте відповідно команду вище
або `docker compose restart telegram`. Не запускайте інший polling із тим самим токеном.

У Telegram надішліть `/menu`. Усі учасники дозволеної групи можуть викликати команди —
це контроль Chat ID, не персональний контроль User ID усередині групи.

## Поведінка повідомлень і стану в режимі Telegram

- При старті перевіряється джерело, завантажуються сьогоднішні й завтрашні графіки.
  Перше завантаження створює базовий стан без чотирьох повідомлень «змінено».
- Порівнюються нормалізовані інтервали та стан публікації кожної черги й дати.
  Зміна HTML, порядку інтервалів або часу оновлення не створює сповіщення.
  Справжнє повернення A → B → A є двома змінами.
- Зміна графіка надходить окремим повідомленням з оповіщенням, номером черги
  й прогнозом ліфта. Повідомлення залишається в історії без редагування.
  Зміни завтра теж відстежуються.
- Ранковий звіт — щодня о 08:00 за Києвом (або `MORNING_REPORT_TIME`), окремим
  повідомленням з оповіщенням, один на дату та дозволений чат. Якщо бот був вимкнений о 08:00,
  після запуску того самого дня звіт надходить один раз із поточними даними.
- За 15 хвилин (або `WARNING_BEFORE_MINUTES`) до вимкнення квартири та окремо
  до можливого простою ліфта надходять нові повідомлення з оповіщенням.
  Вони не замінюють меню або попередні сповіщення. Нагадування перевіряються
  кожні 5 секунд, незалежно від 10-хвилинного опитування
  джерела. Новий графік, опублікований менш ніж за 15 хвилин до початку, спричиняє
  негайне попередження, якщо подія ще не почалася.
- Застарілі pending-нагадування скасовуються. Після перезапуску вони відновлюються
  з актуальних даних SQLite. Однаковий початок події не нагадується вдруге навіть
  при зміні її завершення. Зміна початку створює іншу подію.
- Минулі події не нагадуються; поточні інтервали залишаються у денному звіті.
  Інтервали суміжних днів зливаються, щоб не попереджати вдруге про продовження
  відключення після півночі.
- `maybe/mfirst/msecond` зберігаються окремо від планових відключень квартири.
  Прогноз ліфта консервативний: включає перетини планових **або можливих** відключень
  обох ліній. У звіті можливі відключення позначені окремо.
- Немає графіка хоча б однієї лінії — немає достатніх даних для прогнозу ліфта.
  Порожній опублікований графік і відсутній графік — різні стани.
- При збої джерела останні дані залишаються. У `/status` є час спроби, останнього
  успішного отримання та помилка; у звітах — час отримання й оновлення джерелом.
  Після 30 хвилин без успішної перевірки звіт позначається застарілим,
  а попередження за таким планом призупиняються. Датований план може лишатися
  незмінним багато годин: давній час його публікації показується окремо й сам по
  собі не означає, що актуальна успішна перевірка не відбулася.

### Межа гарантії відсутності дублів

Дані графіка та outbox повідомлень про зміни записуються однією SQLite-транзакцією.
Ключі ранкових звітів і нагадувань зберігаються у volume. Перед `sendMessage` подія
позначається `sending`, після успіху — `sent`.

Telegram не надає idempotency key для `sendMessage`. При обриві з'єднання або аварії
між прийняттям повідомлення Telegram і записом підтвердження неможливо одночасно
гарантувати доставку та відсутність дублів. Тут обрано захист від дублів: така подія
стає `uncertain` і автоматично не повторюється. Вона могла бути доставлена або
втрачена; кількість видно в `/status`. Явна відмова через ліміт Telegram повторюється
після `Retry-After`; явні 400/403 стають `failed`. Це не обіцянка exactly-once доставки.
Для основного допису з меню використовується `editMessageText`. При помилці редагування
нове повідомлення не створюється, за винятком явної відповіді про видалений або
недоступний для редагування допис. Після успіху чи `message is not modified`
зберігається останній відбиток вмісту; однаковий вміст не надсилається повторно.

### Один polling-процес

При локальному запуску OS-блокування захищає той самий токен на одному хості.
Блокування каталогу SQLite діє також між контейнерами зі спільним volume.
Compose фіксує одне ім'я контейнера; не масштабуйте сервіс. Різні машини або
контейнери з незалежними volume не мають спільного блокування: не використовуйте
там цей самий токен одночасно.
При Telegram 409 процес завершується; налаштований webhook також блокує запуск.
Бот самостійно не видаляє webhook і не відкидає накопичені Telegram updates.
Telegram використовує один кешований `bot.me()` перед polling. Long polling очікує
оновлення до 50 секунд; aiogram задає довший клієнтський timeout.
При 429, мережевих помилках і 5xx діє спільна пауза перед новими API-запитами:
10, 20, 40, 80, 160, 300 секунд, після сьомої послідовної невдачі — по 15 хвилин.
Для 429 береться більше з backoff і `retry_after`; додається випадковий запас 2–5 секунд.
Лічильник скидається після успіху відповідного методу. Пауза зберігається в SQLite,
тому перезапуск її не обходить. Неоднозначна доставка повідомлень не повторюється.
Нові запити очікують завершення паузи; уже відкритий long polling може завершитися.
Перевірки ДТЕК продовжуються навіть під час початкового очікування Telegram.

На рівні HTTP-сесії записуються початок і результат кожної спроби, метод, номер
спроби, тривалість, отриманий HTTP-код і `retry_after`, без токенів та тіл повідомлень.
Кожні 60 секунд є `telegram_request_summary`: кількість спроб за методами,
частота за хвилину та кількість одночасних запитів. Деталі й порядок перевірки:
[діагностика Telegram](docs/telegram-diagnostics.md).

## Команди та кнопки

| Команда | Результат |
|---|---|
| `/start` | Допомога й клавіатура |
| `/menu` | Показати кнопки керування |
| `/today` | Дві черги та ліфт сьогодні |
| `/tomorrow` | Дві черги та ліфт завтра |
| `/lift` | Прогноз ліфта на обидва дні |
| `/status` | Перевірки, успішне отримання, помилки, стан доставки |
| `/ping` | Швидка відповідь бота з київським часом |
| `/help` | Пояснення роботи |

Кнопки «Сьогодні», «Завтра», «Ліфт», «Стан моніторингу», «Перевірити бота» й «Допомога»
розміщені під одним основним дописом. Відповіді на команди перемикають його вміст.
Ранковий звіт, зміни графіка й нагадування надсилаються через `sendMessage`
з `disable_notification=false`: кожна подія має окреме повідомлення, яке не редагується.
Кнопки під сповіщеннями також відкривають результат в основному дописі з меню.
«Ліфт» показує обидва дні разом.
Посилання на джерело є лише в `/status`.

Натискання кнопки не додає текстового повідомлення користувача: бот підтверджує
`callback_query` і за потреби редагує допис. Фонових оновлень за таймером не додано.
Ідентифікатор допису зберігається у SQLite; паралельні команди використовують
спільне блокування чату. Якщо допис видалено, `/menu` або `/start` відновить його.
Стара історія до цього оновлення й вручну введені команди залишаються в чаті.
Звук і push для нових сповіщень залежать також від налаштувань чату та пристрою.

`/ping` оновлює допис із часом відповіді без додаткового запиту до ДТЕК або перевірочного
виклику Telegram API. Для команд Telegram-процес має продовжувати працювати.

Неавторизовані чати не отримують відповіді та не потрапляють у список підписників.
Токен і API-ключ маскуються в логах; `.env`, SQLite, локальні інструменти й сирі
дослідницькі завантаження виключені з Git та Docker build context.

## Перевірка, перезапуск та обслуговування

```bash
# Healthcheck перевіряє моніторинг та вебсервер; у telegram — polling і нагадування.
docker compose exec bot python healthcheck.py
docker inspect --format '{{.State.Health.Status}}' odesa-power-lift-bot

# Після цього /status має зберегти історію, повторного ранкового звіту не має бути.
docker compose restart bot
docker compose logs --tail=50 bot

# Оновлення коду та образу, volume зберігається.
git pull --ff-only
docker compose up -d --build

# Зупинка без видалення стану.
docker compose down
```

`restart: unless-stopped` перезапускає процес після аварії та при завантаженні Docker.
Сам Docker не перезапускає контейнер лише через статус `unhealthy`; healthcheck
призначений для діагностики/зовнішнього нагляду. Недоступність ДТЕК сама по собі
не робить живий процес unhealthy — застосунок продовжує показувати кеш і повторювати перевірки.

Не використовуйте `docker compose down -v`, якщо потрібна історія: ця команда
видаляє volume. Зберігайте SQLite на локальному диску Linux, не на мережевій FS.
Історія та завершені події зберігаються 90 днів, після чого очищуються.
Для резервної копії використовуйте SQLite backup API, а не копіювання одного файлу
під час активного WAL:

```bash
docker compose exec bot python -c "import sqlite3; a=sqlite3.connect('/app/data/bot.sqlite3'); b=sqlite3.connect('/app/data/backup.sqlite3'); a.backup(b); b.close(); a.close()"
docker compose cp bot:/app/data/backup.sqlite3 ./backup.sqlite3
```

## Локальний запуск і тести

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements-dev.txt
ruff check .
pytest -q
python -m schedule_provider --check
python main.py
```

Тести не потребують токенів або інтернету: мережеві відповіді ізольовані через
`httpx.MockTransport`. У `tests/fixtures` є скорочений справжній знімок ДТЕК
за 23.11.2026 лише для перевірки парсера. Робочий адаптер його ніколи не читає.
CI перевіряє Python 3.11/3.12/3.13, Ruff, pytest, складання Docker-образу,
доступність сторінки, API й healthcheck в контейнері з порожнім Telegram-токеном.

Перевіряються перетини, суміжність, північ, минулі інтервали, 23/25-годинні дні,
відокремлення операторів, реальний формат ДТЕК, 401/403/429/503, невідомі/відсутні
дані, нормалізовані зміни сьогодні/завтра, атомарність запису, скасування нагадувань,
перезапуск і дедуплікація, невизначена доставка, Chat ID та блокування процесів.

## Модулі

- `main.py` — вибір вебрежиму або Telegram, контроль життєвого циклу та маскування секретів.
- `telegram_client.py` — кеш, спільний backoff та вимірювання Telegram HTTP-спроб.
- `telegram_messages.py`, `telegram_ui.py` — один збережений допис на чат та inline-навігація.
- `web_dashboard.py`, `static/` — вебсервер, read-only JSON API та адаптивна сторінка.
- `bot.py` — команди, клавіатура, контроль Chat ID.
- `schedule_provider.py` — перевірені адаптери й команда `--check`.
- `monitor.py` — перевірки, зміни, ранковий звіт, планування нагадувань.
- `lift.py` — нормалізація, перетини, північ і часовий пояс.
- `notifications.py` — українські повідомлення та доставка outbox.
- `database.py` — SQLite, історія, дедуплікація, відновлення стану.
- `config.py`, `models.py`, `instance_lock.py`, `healthcheck.py` — налаштування та інфраструктура.

## Обмеження

HTML ДТЕК не є версіонованим API. Захист сайту, зміна його формату або відсутність
актуальних дат можуть тимчасово зупинити оновлення; це видно на вебсторінці або в `/status`.
За потреби можна свідомо обрати платний документований API. Фактичні аварійні
відключення та стан перемикання ліфта графіками не вимірюються. Аварійні повідомлення
ДТЕК слід перевіряти вручну: HTML-адаптер не інтерпретує довільні банери як достовірний
машинний статус. API-стан `EmergencyShutdowns`, коли він доступний, відображається явно.

Бот починає надсилати Telegram-повідомлення лише після додавання власного токена
та дозволених Chat ID. Самої наявності коду в репозиторії недостатньо для роботи 24/7.
